1  Purpose & Context
A working prototype of the clinic CRM already exists — a full-featured HTML app backed by Google Apps Script and 
Google Sheets. It establishes the exact features, screens, and data a clinic needs day-to-day. The goal of this module is to 
rebuild that validated design on our production stack (FastAPI + PostgreSQL + Next.js) so it runs as part of the same 
system that already powers the Posture Tool and Exercise Library.
1.1 Why the prototype is a reference, not a codebase to port
Google Sheets cannot serve as the database for a multi-clinic SaaS product — it does not provide the concurrency, data 
isolation between clinics, or reliability required for patient data. The prototype is also single-clinic by design (one sheet = 
one clinic), so it has no concept of many clinics sharing one system. We therefore take its feature set and data as the 
blueprint, and implement it fresh on a proper multi-tenant relational database.
1.2 Reference material
• Tarun (frontend): you'll receive the prototype UI file (crm.docx) as a visual reference for the screens, tabs, and 
layout. Use it to understand what to build — not how to build it. Follow the component structure and design tokens 
already used in the Posture Tool and Exercise Library frontends; do not carry over the prototype's HTML, CSS, or JS.
• Sparsh (backend): everything you need — the data model, endpoints, and rules — is defined in this document. Build 
against this specification. If a requirement isn't covered here, flag it before building rather than inferring it from the 
prototype.

2  Engineering Standards — Read Before Writing Any Code
These are non-negotiable standards for this module. Treat any violation as a bug.
STANDARD 1 — EVERY TABLE AND EVERY QUERY IS SCOPED BY CLINIC_ID
This is a multi-tenant system: many clinics share one database. A case where Clinic A can read or edit Clinic B's data 
is a data breach, not a minor issue. Use the existing ClinicGateMiddleware (backend/app/middleware/clinic_gate.py) 
— do not write separate scoping logic. Any new table holding clinic-specific data must carry a clinic_id foreign key, 
and every SELECT/UPDATE/DELETE on it must be filtered by the authenticated user's clinic_id.
STANDARD 2 — NO PUBLIC FILE OR DOCUMENT ROUTES
Every endpoint that serves a PDF, image, or document (invoices, prescriptions, patient documents) must require a 
valid JWT and verify the file belongs to the requester's clinic. There are no public or unauthenticated file routes 
anywhere in this system. Files live in a private Supabase Storage bucket and are served only through authenticated, 
clinic-scoped endpoints.
STANDARD 3 — REUSE THE SHARED BUILDING BLOCKS
Auth (JWT + bcrypt), the response-envelope pattern, ClinicGateMiddleware, and WeasyPrint PDF generation already 
exist and are in use. Import and reuse them. Do not add a second auth system or a second PDF pipeline.
STANDARD 4 — ONE SHARED BACKEND
backend/app/main.py and the Alembic migration history are shared across the Posture Tool, Exercise Library, and 
CRM. Never recreate main.py, and never redefine a model (User, Clinic, Patient) that already exists — extend it with 
a migration. After every merge, confirm main.py still registers all middleware and routers (ClinicGateMiddleware, 
logger, settings, api_router) — standard merge hygiene.
STANDARD 5 — CONNECT TO POSTGRES THROUGH THE POOLER
Use the Supabase connection pooler (Supavisor, transaction mode, port 6543) in the async SQLAlchemy engine URL 
— not the direct port 5432. This lets many requests share a small pool of real database connections. Confirm 
DATABASE_URL uses the pooler port before merging.
STANDARD 6 — SUBMIT COMPLETE FILES FOR REVIEW
When submitting a change for review, share the complete file rather than a diff or patch — it keeps line endings 
consistent and review unambiguous.

3.3 The CRM is the anchor of the suite
A patient exists once, in one place. A posture analysis attaches to that patient's record; an exercise prescription attaches to 
the same record. This is the core integration point of AV Suite and what makes it more than a practice-management tool. 
The Patients table built in Phase 1 is what the Posture Tool and Exercise Library will both point to.

All endpoints sit under /api/v1/, require a valid JWT (except the public booking routes), and are clinic-scoped via 
ClinicGateMiddleware. Follow the existing response-envelope pattern.

6  Build Plan
This is a one-week sprint. Both of you work against it daily and self-organize on who owns what within each workstream. 
Sync Monday and Thursday — blockers only. Build in the order below; Phase 1 is the foundation everything else depends 
on, so it lands first, with Phases 2 and 3 following as it stabilizes.
Phase 1 — Foundation
• Clinics + Users tables + migration. First confirm whether a Clinics table already exists from earlier work — do not 
create a duplicate.
• Wire ClinicGateMiddleware to the Users/Clinics model.
• Auth: login endpoint issuing a JWT with clinic_id + role in the claims.
• Patients CRUD and Appointments CRUD, fully clinic-scoped.
• Done when: two test clinics exist, each with their own users and patients, and a passing test proves Clinic A's token 
cannot read Clinic B's patients.
Phase 2 — Clinical & Billing
• Treatments / Assessments (SOAP) linked to appointments.
• Packages, Patient Packages, Invoices, Payments.
• Invoice PDF via the existing WeasyPrint service.
• Patient Documents upload/download — private Supabase Storage only.
• Done when: a patient can be invoiced, paid, and the invoice downloaded as a PDF only by an authenticated user of 
the correct clinic.
Phase 3 — Growth & Ops
• Leads + kanban stage transitions + convert-to-patient.
• Public booking form + AppointmentRequests + approve/reject flow.
• Analytics overview + dashboard cards.
• Recycle Bin (soft-delete) + Audit Logs + Settings (clinic branding).
• Done when: a lead from the public booking form can be approved into an appointment, with the audit trail visible in 
Settings.

7  Non-Functional Requirements
7.1 Security
• Every request touching patient data carries a valid JWT and passes through ClinicGateMiddleware.
• No patient data (name, phone, condition, documents) appears in any public response.
• Passwords: bcrypt only, via the existing security module — never stored or logged in plaintext.
7.2 Performance
• Expected load is well within Supabase Pro limits — the priority is query quality, not capacity. Add indexes on 
clinic_id, patient_id, and any column used in a WHERE filter.
• Use the Supabase connection pooler (Standard 5).
7.3 Data integrity
• Foreign keys enforced at the database level, not only in application code.
• Soft-delete (deleted_at) for anything in the Recycle Bin — never hard-delete patient-related records.
7.4 Testing
• Every new endpoint gets at least one test proving clinic isolation — the most important test category in this module.
• Follow the existing test patterns in backend/tests/.

9  Working in a Shared Codebase
The CRM lives in the same repo and the same backend as the Posture Tool and Exercise Library — that's deliberate: it's 
what lets a patient exist once and have their posture reports and prescriptions attach to that same record. It also means a few 
habits matter more here than they would in a standalone project. These are small things, and getting them right from day 
one will save us both a lot of pain later.
For Sparsh — Backend
You're building the foundation the entire suite sits on. Three habits, specific to working in a shared backend:
• Check for a single migration head before every merge. Run alembic heads — if it returns more than one head, stop 
and rebase rather than merging. Two heads will break the deploy for all three tools, and it's much easier to prevent 
than to untangle afterwards.
• Register routers in api/v1/__init__.py, not in main.py. main.py is shared by every tool, so the less it changes, the 
fewer merge conflicts we all hit. Keep it thin — add your router to api_router and main.py never needs touching.
• The CRM owns Clinic, User, and Patient. These are the shared models the other tools reference by foreign key. 
Extend them through a migration when you need to — but they're yours to define, and nothing else should be 
redefining them. If you ever find a second definition somewhere, flag it.
Beyond that: clinic-scope every query, keep endpoints consistent with the existing envelope pattern, and write the isolation test as 
you build rather than after. You'll enjoy Phase 2 a lot more if Phase 1 is solid.
For Tarun — Frontend
You're building what the clinic actually sees and touches every day, so polish here is the product. A few things worth 
keeping in mind:
• Match the existing design language. The Posture Tool and Exercise Library frontends already establish our 
component structure and design tokens. Follow them — the CRM should feel like the same product, not a third app 
bolted on.
• Use the prototype for what, not how. crm.docx shows the screens, tabs, and layout we want. Take the structure and 
the intent from it; build it fresh in Next.js + Tailwind. If something in it conflicts with this specification, the 
specification wins — flag it and I'll clarify.
• Build against the API contract in Section 5. The endpoints are defined there, so you're not blocked waiting on the 
backend — mock the responses and build the screens in parallel. If an endpoint you need isn't specified, tell me before 
assuming its shape.
Beyond that: this is a tool physios will use for hours a day, so favour clarity over cleverness — fast, obvious, forgiving. Loading 
states, empty states, and error states are part of the work, not an afterthought.
BOTH OF YOU
You're working on the same foundation from two sides, so a quick message to each other before touching something 
shared is always cheaper than untangling it afterwards. Ask early, ask often — that's not friction, that's the job.

10  Flag Before You Guess
If you hit any of the following, raise it before building rather than assuming an answer:
• Whether a Clinics or Users table already exists from earlier work — confirm before creating a new one.
• Any business rule not explicitly in this specification (e.g. how partial payments against a package are handled) — do 
not invent business logic.
• Any point where the prototype UI conflicts with this specification — this specification wins; flag the conflict rather 
than silently following the prototype.
