# Tool 03 Psycho-Social Screening: Known Limitations

| ID | Limitation | Impact | Planned fix |
|---|---|---|---|
| S-L-001 | The screener rate limiter is in-process. On more than one replica, each replica keeps its own counters. | Railway runs 1 replica today, so no impact now. With N replicas the real limit is N times higher. | When scaling out, move the counters to a shared store (Redis or Postgres). |
| S-L-002 | No column-level encryption. At rest we rely on Supabase disk encryption, in transit on HTTPS. | Meets SRS 3.2 at infrastructure level only. Column encryption needs a key-management decision. | v1.1 or later, after a founder decision. |
| S-L-003 | The SRS refers to `AV_Suite_Clinical_Reference_v1.xlsx` (Severity_Logic sheet) for referral thresholds. We do not have it yet. Thresholds come from SRS 2.2 and 4.1.3 and the published papers. | If the sheet differs from published norms, published norms win and the gap gets an entry in Decisions.md (Onkar, 20 Oct). | Compare when Onkar uploads the file (P-05). |
| S-L-004 | The link token sits in the URL path, so it appears in request logs (Railway, Vercel). | Anyone with log access could open an unfinished screener. They would see questions and saved answers but no identity and no score. | Accepted for v1 like the booking page. Possible fix later: exchange the token for a short-lived cookie on first open. |
| S-L-005 | Closed 22 Oct 2026. Deletion on request is built (S-D-024): the clinic admin deletes a patient's screening data from the patient page. | None. | Done. |
| S-L-006 | After a patient withdraws consent there is no way back. Only the patient can grant consent, and a withdrawn patient gets no new link. | A patient who changes their mind cannot be screened again. | Founder decision needed (for example, the physio records in-person re-consent). |
| S-L-007 | Admins have `screening.assign` but not `screening.view`, so an admin can send a link but cannot see or cancel it afterwards. | Small workflow gap for admin-sent links. | Revisit with the founders' F3 and F5 answers. |
| S-L-008 | An admin can grant themselves `screening.view` through the permissions endpoint. | Bypasses the SRS 3.2 intent, but every grant is in the audit log. | Revisit with F3. |
| S-L-009 | Not built yet (done 22 Oct: trend chart and PDF summary S-D-025, repeat schedules S-D-026, default repeat per screener S-D-027, anonymised statistics and CSV S-D-028): editable referral thresholds, patient own-history view, referral contact directory, CRM patient tab, Exercise Library context. | SRS 4.2.3, 4.3.1 (referral contacts), 4.3.2 item 2 (editing), 5.2 and 5.3 are open. Full status per requirement in DoD_Checklist.md. | v1.1 (P-12). |
| S-L-010 | Staff accounts are created only in the CRM's user management. A screening-only clinic has no screen for that. | Such a clinic needs the CRM UI or an API call to add staff. | Decide with the founders. |
| S-L-011 | Deletion works only for patients who are active in the clinic. If the CRM has moved a patient to the recycle bin, their screening data cannot be deleted from the screening app. | A deletion request for such a patient needs the patient restored first, or a manual database step. | Decide with the CRM Project whether removing a patient should also remove their screening data. |
| S-L-012 | After a deletion, audit events from before it remain. They hold the patient id and screener names (for example "phq9"), never answers, scores or flags. | The audit log still shows that a patient was screened and when. | Accepted for v1: the audit trail is a record of actions, and it carries no clinical values (S-D-015). Revisit if legal review of the DPDP position asks for it. |
| S-L-013 | The PDF file name comes from the browser, not from the server's Content-Disposition header, because the backend CORS setup does not expose that header to another origin. Both use the same pattern (`screening-summary-<name>-<date>.pdf`). | None for the user. The name can differ only if the browser and server dates fall either side of midnight IST. | Expose Content-Disposition in the shared CORS config when the CRM Project next changes it. |
| S-L-014 | Repeat schedules do not notify anyone. A due screener appears in "Due again" and on the patient page only. | A physio who does not open the app will not notice it is due. | Revisit with founder question F4 (real-time alerts); an email that says only "screenings are due" would fit. |
| S-L-015 | Referral thresholds are shown on the Settings page but cannot be changed by a clinic (S-D-027). | Every clinic uses the published norms. SRS 4.3.2 item 2 is Partial. | Founder decision first, then the build listed in P-13. |
| S-L-016 | The Repeat field says "Just once" even when the ticked screener already repeats for the patient. Sending with Just once keeps that repeat, and the drawer says so in a line under the field. | Wording can confuse until the hint is read. | A clearer option such as "Keep the current repeat" when the drawer is next reworked. |
| S-L-017 | Statistics hide small counts, but when everyone in a period falls in one band (for example all 7 in Moderate), the page shows 7 in that band. Someone who knows a person was screened then knows their band. | Low with a 90-day default range and real clinic volumes, higher for a narrow date range in a small clinic. | Review with real pilot numbers (Review_Points.md). Options: a minimum range length, or hiding a band that holds the whole group. |
| S-L-018 | Statistics are computed per request in Python from every completed screener in the range. | Fine for one clinic's volume. Slow for very large clinics or long ranges. | Before scale: move the counting to a SQL GROUP BY with an index on `(clinic_id, status, completed_at)` (Review_Points.md). |
